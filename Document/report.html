01
GenAI Prompts

The three prompts below were used to generate the products filter, the registration flow, and the login route. They are recorded here verbatim so the generation steps are reproducible and auditable.

Prompt 1 — Products Filter (GET /api/products)
You are a backend assistant. Build an Express route for GET /api/products. The request envelope includes a query parameter: category. Implement gatekeeper logic: allow only when category equals "hat" (case-insensitive). On success, read local products.json, filter products by category (match in title), and respond with JSON { status: "success", data: Product[] }. On failure (gatekeeper or server error), respond with JSON { status: "fail", message }. Add brief comments in code explaining envelope, gatekeeper, and package.

Implementation note: The gatekeeper rejects any non-"hat" category with a 400. Filtering uses a case-insensitive substring match against title, so a future category=chair would also work if the gatekeeper were relaxed.

Prompt 2 — User Registration (POST /api/register)
You are a full-stack assistant. Implement user registration. Backend: Express POST /api/register. Expect JSON body { name, email, password }. Check if email already exists in auth_user.json. If exists, return 409 with { status: "fail", message }. If new, hash password with bcrypt and store user in auth_user.json. Return 201 { status: "success", message }. Frontend: register.js should validate password rules before sending: at least 8 characters, at least 1 uppercase, at least 1 special character (!@#$%^&*). Show clear error messages and redirect to login on success. Add brief comments explaining the flow in both route and register.js.

Implementation note: bcryptjs is used with the default cost factor (10). Two gatekeepers run in series — the frontend gatekeeper blocks weak passwords before any network call, and the backend gatekeeper re-validates and checks for duplicates because the client cannot be trusted.

Prompt 3 — User Login (POST /api/login)
Act as a Security Engineer. Write a Node.js/Express POST route for /api/login. Receive { email, password } in the request body. If either field is missing, return 400. Look up the user in data/json/users.json by username (= email). If the user is not found, return 401 Unauthorized. If found, hash the submitted password with MD5 (assignment requirement) and compare with the stored hash. On mismatch, return 401. On match, sign a JWT containing { userId } using JWT_SECRET from process.env (fallback "dev-secret") with expiresIn: "1h", and return { status: "success", token }. Wrap the handler in try/catch and return 500 with { status: "fail", message } on unexpected errors.

Implementation note: MD5 is used here only because the assignment specifies it for the seed users.json dataset. In production, MD5 is unsuitable for password storage — bcrypt (used in registration) should be the standard. JWTs are signed server-side; the secret must come from an environment variable, never from source code.

3.6 Security & Design Decisions

DecisionReason
Two gatekeepers for register (frontend + backend) The frontend gatekeeper (register.js) gives instant feedback and avoids unnecessary requests, but the client cannot be trusted — the backend re-validates the same rules and additionally checks for duplicate email.
bcrypt for register, MD5 for login (legacy seed data) New accounts in auth_user.json use bcrypt with cost factor 10 (slow + per-hash salt → resists brute-force). The seed dataset users.json uses MD5 only because the assignment specifies it; this is documented as a known weakness, not a recommendation.
Same 401 message for "user not found" and "wrong password" Returning distinct messages would let an attacker enumerate which emails are registered. A single generic "Unauthorized" response leaks nothing.
JWT payload contains only { userId } JWTs are Base64-decodable by anyone holding the token. Sensitive fields (password hash, email, address) must never appear in the payload.
JWT_SECRET from process.env Hardcoding secrets in source exposes them in git history. The "dev-secret" fallback is for local dev only and must be overridden in any deployed environment.
CORS allowlist (127.0.0.1:5500 / localhost:5500) The Live Server origin is explicitly whitelisted instead of using "*". This blocks cross-origin requests from arbitrary sites attempting to call the API on a logged-in user's behalf.
Envelope / Gatekeeper / Package vocabulary in code comments Each controller and service carries one-line comments labelling these three phases. This matches the conceptual model taught in the WebTech course and makes the intent of each block visible at a glance during code review.
